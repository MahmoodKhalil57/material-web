Spec compliance

What the spec checks, ARIA and axe results, Baseline use and size budgets say about md-gb-* components.

View as Markdown

How compliance is measured

Link to “How compliance is measured” #

The numbers on this page come from the repository itself and are regenerated by node scripts/m3/gen-compliance-page.mjs (--check fails when this page is stale). The M3 spec is downloaded with npm run m3:update, split into units (a sentence, list item, table row or image description, each with an id), and node scripts/m3/spec-checks.mjs --offline records what happens to each one in .m3-specs/spec-checks/units.json. Only unit counts and ids are used here, never spec text.

Spec units

Link to “Spec units” #

A unit is buildable when the classifier scores it at 0.3 or more (it describes something a component can do, not a caption or designer advice). Tested units are cited from a *_test.ts file under labs/gb or scripts/m3 (spec: <unit id>). Excluded units have a written reason in scripts/m3/exclusions/*.md (spec-exclude:). Tracked units are known gaps listed in scripts/m3/CHECKLIST.md (spec-gap:). Uncovered units are buildable, with no status and no test; the target is 0.

Token audit

Link to “Token audit” #

node scripts/m3/audit-gb.mjs --gaps compares every token declaration in the labs/gb token files with the M3 token database. Match means the value equals the spec; derived means it is computed from a matching token; drift differs from the spec; no spec token has no counterpart in the database; gaps are tokens the Compose reference uses that no gb declaration implements.

Overall: 2415 declarations, 1949 match, 23 derived, 10 drift (0 high-confidence), 433 with no spec token, 10 spec tokens not implemented.

Accessibility

Link to “Accessibility” #

Two central suites render rows in labs/gb/components/shared/central and run in a real browser:

  • axe (axe_test.ts): axe-core with no rule disabled, on every subject of the central table (subjects.ts) plus 29 overlay rows in their open state (axe-helpers.ts).
  • ARIA 1.3 (aria_test.ts): the axe rows plus 34 rows that put components in the states ARIA depends on (selected, checked, expanded, grouped, with panels, with an error), checked against the WAI-ARIA 1.3 role and attribute rules. 27 rows are open overlays, so the checks that flip state skip them.

Known gaps are rows with a real violation. They move to axe_gap.ts and aria_gap.ts (red on purpose) and are recorded in AXE_GAPS and ARIA_GAPS. Today: axe none; ARIA none. Suite files: aria_gap.ts, aria_test.ts, axe_gap.ts, axe_test.ts.

Baseline

Link to “Baseline” #

npm run gb:baseline maps every CSS feature in the compiled labs/gb CSS to its web-features Baseline status. A feature that is not widely available must sit inside a matching @supports guard or be listed with a reason in scripts/gb-baseline-allow.json; anything else fails the run.

  • CSS: 19,541 feature uses in 62 files; 51 features are not widely available, used 754 times (478 guarded, 276 allowed with a reason, 0 unguarded). Result: passes.
  • JavaScript (report only): 31 tracked Web API members in 207 source files; 6 are not widely available, 3 of them with at least one use that is not feature-detected.
